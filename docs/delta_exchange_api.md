# Delta Exchange V2 API Technical Reference Guide

This document provides a highly detailed, production-grade technical analysis of the **Delta Exchange V2 REST API**. It serves as a master integration manual for engineers developing low-latency execution algorithms, background synchronizers, and analytical trade matching pipelines.

---

## 1. Request Structure & Authentication

All private (authenticated) REST requests interacting with the Delta Exchange endpoints require strict verification utilizing HMAC-SHA256 signature headers. 

### Mandatory Headers

All authenticated request headers must be populated exactly as defined below:

| Header Name | Type | Description |
| :--- | :--- | :--- |
| `api-key` | `string` | The API Key generated from the user's Delta Exchange API console. |
| `signature` | `string` | A hex-encoded signature string (detailed below). |
| `timestamp` | `string` | A standard Usec/Sec Unix timestamp corresponding to signature generation time. |
| `User-Agent` | `string` | A descriptive identifier mapping client context (e.g., `python-rest-client` or `rest-client`). **Mandatory; omission triggers 4XX exceptions.** |
| `Content-Type` | `string` | Must be configured to `application/json` for all POST, PUT, and DELETE payloads. |

### Signature Generation Algorithm

The signature header validates data integrity and authentication. It is generated by hashing a concatenated **pre-hash message string** with the user's `DELTA_API_SECRET` using a standard SHA256 HMAC cipher. 

#### Pre-hash Format
The message string is built by strict concatenation (without delimiters or padding) of the following parameters in order:

$$\text{Signature Pre-hash} = \text{HTTP\_Method} + \text{Timestamp} + \text{RequestPath} + \text{QueryParameters} + \text{RequestBody}$$

*   **HTTP\_Method**: uppercase REST verb (e.g., `GET`, `POST`, `PUT`, `DELETE`).
*   **Timestamp**: The exact string sent inside the `timestamp` header (usually Unix seconds epoch).
*   **RequestPath**: The API relative endpoint path (including the prefix version, e.g. `/v2/orders`).
*   **QueryParameters**: The complete literal query-string as sent in the URL starting with `?` (e.g., `?product_id=1&state=open`). For requests with empty query structures, this parameter is empty (`""`).
*   **RequestBody**: The exact serialized JSON raw string payload. For empty bodies (such as standard GET queries), this parameter is empty (`""`).

#### Python Signature Compilation Snippet
```python
import hmac
import hashlib

def generate_delta_signature(secret: str, method: str, timestamp: str, path: str, query: str = "", body: str = "") -> str:
    # Compile raw pre-hash message
    message = f"{method}{timestamp}{path}{query}{body}"
    
    # Encode key and payload
    secret_bytes = bytes(secret, "utf-8")
    message_bytes = bytes(message, "utf-8")
    
    # Hash utilizing HMAC-SHA256
    hash_obj = hmac.new(secret_bytes, message_bytes, hashlib.sha256)
    return hash_obj.hexdigest()
```

> [!IMPORTANT]
> **5-Second Signature Window**: Delta Exchange enforces a maximum drift threshold. If the signature arrives at the exchange gateway more than **5 seconds** after its generated timestamp, the request is instantly rejected (prevents replay attacks).

## 2. API Data Types & Constraints

Precision is critical for trading applications. The Delta V2 API uses specific constraints to eliminate truncation and decimal-parsing issues:

### Numbers & Decimal Precision
*   **Strings for Precision**: To avoid floating-point rounding errors and truncation during transport, all floating-point numbers (such as `limit_price`, `stop_loss_price`, `trail_amount`, and `pnl` variables) are returned as **JSON Strings** containing full fractional precision. 
*   **Raw Numeric Types**: Pure integers (such as `contract_size`, `product_id`, `impact_size`) are transmitted as native, unquoted JSON numbers.

### Timestamps
*   Unless explicitly specified on low-level options, all API timestamps are reported as standard **ISO-8601 strings** down to microsecond levels (e.g., `2026-05-22T23:46:16.000Z`).

### Unique Identifiers (IDs)
*   **Product & Asset Identifiers**: Provided as big integer numbers (e.g., `product_id: 27`).
*   **Client Order IDs (UUIDs)**: UUID fields accept formats both with and without hyphen markers (e.g., `167ja7cg-678e-6876-d6g3-f803ce49qsc9` or `167ja7cg678e6876d6g3f803ce49qsc9`).

## 3. Rate Limiting, Weights, & Cost Structure

To ensure exchange stability, Delta enforces a dual-layered throttling architecture:

### 1. REST Gateway Level (IP & User ID Throttling)
*   **Unauthenticated API Queries**: Throttled at the client IP address level.
*   **Authenticated API Queries**: Throttled at the individual User ID profile level.
*   **Default Quota**: **10,000 units** assigned per a rolling **5-minute window**. 
*   **Weight Deduction**: Every API endpoint has an assigned cost metric. When queried, this cost is deducted from the user's active 5-minute quota window.

#### Endpoint Cost Weights (Non-Exhaustive)
*   **GET Market Info / Public Assets**: Weight = `1 unit` (default).
*   **GET Account Balances / Assets**: Weight = `3 units`.
*   **GET Open Orders**: Weight = `3 units`.
*   **POST Place New Order**: Weight = `5 units`.
*   **POST Batch Orders (Multi-leg operations)**: Weight = `25 units`.

#### Limit Breach Error Handling
When a rate limit is breached, the endpoint returns an **HTTP 429 Too Many Requests** response.
*   **`X-RATE-LIMIT-RESET` Header**: The response contains this custom header specifying the remaining delay in **milliseconds** until the user's quota is reset and requests are processed again.

### 2. Product/Matching Engine Level
*   **Operation Throttle**: In addition to REST gateway quotas, the internal order-matching engine restricts execution limits to **500 operations per second** for each individual product symbol.
*   *Note*: Placing a batch order containing 50 individual orders deducts 50 operations immediately from the matching engine limit. Exceeding this limit will trigger an immediate HTTP 429 even if the REST 5-minute quota has not been breached.

## 4. Response Schemas

To ensure consistent handling, the Delta API structures both successful data retrieval and error responses using standard JSON templates.

### Success Response Format
All successful API transactions return a standardized envelope containing query metadata alongside the requested payload:

```json
{
  "success": true,
  "result": {
    "id": 27,
    "symbol": "BTCUSD",
    "contract_type": "perpetual_futures"
  },
  "meta": {
    "after": "eyJjcmVhdGVkX2F0IjoiMjAyMy0xMi0xOFQxMzoxMDozOVoifQ==",
    "before": null
  }
}
```

*   **`result`**: Contains the target resource data structure (such as trade structures, wallet balances, or order states).
*   **`meta`**: Contains query-specific information, such as cursors (`after` / `before`) for paginated list queries.

### Error Response Format
If a request fails validation, signature matching, or execution checks, a standardized error structure is returned:

```json
{
  "success": false,
  "error": {
    "code": "insufficient_margin",
    "context": {
      "additional_margin_required": "0.121"
    }
  }
}
```

*   **`code`**: A snake_case identifier indicating the exact operational failure reason (e.g. `insufficient_margin`, `signature_expired`, `rate_limit_exceeded`).
*   **`context`**: An optional key-value dictionary detailing the failure parameters (such as outstanding funds needed).
